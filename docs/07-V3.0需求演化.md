# V3.0 需求演化：从运行数据发现的问题

> 实验三 · 校园活动管理系统
> 数据来源：教师提供的模拟运行数据（24 个活动 / 2026-09-21 ~ 2026-10-07）
> 分析脚本：`scripts/analyze_runtime_data.py`，输出见 `analysis/metrics.json`、`analysis/report_tables.md`

## 0. 先说清楚数据能证明什么、不能证明什么

这批数据**不是本组 V2.0 系统产生的**，因此它在本次实验中只承担一个作用：
**作为「哪里可能有问题」的判断依据**，而不是 V3.0 改造效果的证据。
V3.0 的效果一律由本组系统自己的测试与实测数据说明（见实验报告第五部分）。

另外，三组量纲必须分开，混算会直接得出错误结论：

| 量纲 | 数据来源 | 能说明 | 不能说明 |
|---|---|---|---|
| 访问次数 / 事件数 | `user_behavior` 一行一事件 | 页面被打开的频次 | 有多少人遇到了问题 |
| 报名请求数 | `registration_log` 一行一请求 | 提交行为与失败结构 | 有多少独立学生 |
| 人数 | 对 `student_id` 去重 | 覆盖范围 | 行为的强度 |

例如「详情页 5424 次访问」不等于「5424 人看过详情」——去重后是 **393 人**。
本文所有数字都标注了口径。

## 1. 数据事实

### 1.1 规模

| 表 | 行数 |
|---|---:|
| activity | 24 |
| user_behavior | 11027 |
| registration_log | 2878 |
| waitlist_log | 1006 |
| feedback | 112 |
| system_log | 792 |

去重学生 399 人；报名请求 2748 次、取消 130 次；移动端行为占 **71.0%**。

### 1.2 报名请求的结果结构

| 结果 | 次数 | 占报名请求 |
|---|---:|---:|
| accepted | 1689 | 61.5% |
| waitlisted | 876 | 31.9% |
| **duplicate** | **126** | **4.6%** |
| **capacity_conflict** | **41** | **1.5%** |
| **server_error** | **16** | **0.6%** |

失败请求合计 **183 次，占 6.7%**。单看比例不算高，但下面三节说明：
**这三类失败里有两类根本不该以「失败」的形式呈现给用户。**

### 1.3 重复提交：126 次点击，126 次其实都成功了

- 126 次 `duplicate` 请求，`client_retry=1` 的也正好是 126 次——重复提交几乎全部来自客户端重试；
- 涉及 **126 对 (学生, 活动)**、104 名学生、24 个活动；
- 与上一次请求的间隔：**中位数 8.5 秒**，≤10 秒的有 **79 次**；
- 关键事实：**这 126 对组合的最终结果，全部是 `accepted`。**

也就是说：用户第一次点击已经报名成功，但因为等待时间长（P90 1269.6ms）、
页面没有给出确定的结果，他在 8 秒后又点了一次；第二次请求返回「重复」，
被他理解为「报名失败」。**系统把一个成功，讲成了两次失败。**

`capacity_conflict` 同理：平均耗时 **1290.1ms**，是全部结果里最慢的一类，
41 次全部对应日志里的 `E409`。用户等到 1.3 秒后被拒绝，却只得到一个错误码式的结果。

### 1.4 候补：14.8% 的人等到了，但多数人不知道

- 进入候补 876 次，被递补 130 次，**递补率 14.8%**；
- 等待时长：中位数 **18.1 小时**，P90 **46.3 小时**，最长 47.5 小时；
- 被递补的 112 人中，24 小时内访问过状态页的 **33 人（29.5%）**，
  72 小时内 **80 人（71.4%）**——意味着 **32 人在递补后三天内完全没有打开过状态页**；
- 状态页全程只有 **293 次访问，占全部行为事件的 2.7%**。

候补不是「没有结果」，而是**结果发生了、用户没有感知渠道**。等 18 小时以上的事情，
靠用户自己想起来去刷新页面，本身就不成立。

### 1.5 列表：用户在用详情页代替列表做筛选

- 列表浏览 5058 次，详情浏览 **5424 次**，比值 **1.07**——详情比列表还多；
- 看列表的 394 人中，393 人也看了详情；
- **1250 个会话，平均每个会话打开 4.3 个详情页，P90 是 8 个，最多的超过 10 个**；
- 系统中不存在任何筛选类事件（只有 list/detail/status/registration 四种），
  说明产品上没有可用的筛选入口；
- 移动端占 71%，而移动端逐条点开详情的成本更高。

这与反馈完全吻合：「活动标题看着差不多，打开详情才知道具体内容」
「想找周末的活动，试了几次才看到」「我只想参加一类活动，但需要自己逐个看」。

### 1.6 反馈：112 条，其实只有 26 种说法

112 条反馈去重后只有 **26 种模板句**，平均每种重复 **4.3 次**。
所以不能按「多少条反馈说 X」去算用户比例，只能做主题归类，并用其他表交叉验证：

| 主题 | 说法数 | 提交次数 | 交叉验证 |
|---|---:|---:|---|
| 候补结果不可感知 | 6 | 33 | 递补 130 人、72h 内 32 人未查看状态页 |
| 列表信息不足 / 缺少筛选 | 6 | 23 | 详情/列表比 1.07、单会话平均 4.3 个详情 |
| 报名结果不确定 / 失败原因不清 | 4 | 19 | duplicate 126 次、capacity_conflict 41 次 |
| 活动信息完整性（地点、海报） | 2 | 6 | 无行为数据可交叉验证，暂不列入本轮 |
| 正向反馈 | 7 | 27 | — |

**信息完整性只有 6 条、且没有行为证据，本轮不立项**——不因为「有人提了」就做，
这也是数据驱动和「谁声音大听谁的」的区别。

## 2. 需求条目

编号接续 V2.0 的 R-09。每条都标注来源证据与验收标准。

### R-10 报名提交幂等

**来源**：126 次 duplicate，全部来自客户端重试，最终全部 accepted。

**规则**：同一次报名意图的重复提交，必须返回**与第一次相同的结果**，而不是报错。
每次打开详情页生成一个一次性提交令牌；同一令牌的第二次提交直接返回首次结果。

**用户故事**：作为学生，我在网络慢时多点了一次提交，希望看到「你已经报名成功」，
而不是「请勿重复报名」。

**验收标准**：
1. 同一令牌连续提交两次，两次都返回成功语义，数据库中只有 1 条报名记录；
2. 不同令牌重复报名同一活动，返回「你已于 X 提交，当前状态为 Y」，不出现「失败」「请勿」等否定词；
3. 提交按钮在点击后置为禁用态，避免浏览器层面的重复提交；
4. 报名记录数不因重试而增加。

### R-11 失败原因可解释、可行动

**来源**：capacity_conflict 平均 1290ms、server_error 16 次；反馈「没有弄清楚原因」
「提示内容有点难理解」。

**规则**：任何报名失败都必须给出三件事——**发生了什么、为什么、现在能做什么**，
并附一个稳定的错误码供排查。

**用户故事**：作为学生，报名被拒时我要知道是名额满了、截止了，还是系统故障，
以及我下一步该点哪里。

**验收标准**：
1. 每个失败分支有唯一错误码（如 `SIGNUP_FULL`、`SIGNUP_CLOSED`、`SIGNUP_ROLE`）；
2. 结果页同时展示「原因」与「下一步」两个字段，且下一步是可执行的（如「申请候补」）；
3. 可重试的失败（系统错误）明确标注「可重试」，且重试不会产生重复记录。

### R-12 满员竞态自动转候补，不再以错误结束

**来源**：41 次 capacity_conflict 全部以 E409 结束，用户被直接劝退。

**规则**：提交时若名额刚好被占满，不再返回冲突错误，而是**自动进入候补队列**，
并在结果中说明「你提交时名额刚满，已为你排在第 N 位」。

**验收标准**：
1. 容量为 1 的活动，第二人提交后状态为候补，不出现失败提示；
2. 结果页显示候补位次与「有人取消会自动补位」；
3. 名额占用仍准确：正式名额不超过容量。

### R-13 报名结果落地页

**来源**：P90 等待 1.27 秒、重复点击 8.5 秒后才发生；一闪而过的提示不足以消除不确定。

**规则**：报名提交后进入一个**可回看的结果页**，展示活动、当前状态、下一步与时间戳；
刷新页面不会重复提交。

**验收标准**：
1. 提交后落地到结果页，显示状态徽标与「下一步」；
2. 直接刷新结果页不产生新的报名请求；
3. 结果页提供「查看我的报名」与「返回活动」两个出口。

### R-14 状态变化通知

**来源**：递补 130 人，72 小时内 32 人未查看状态页；反馈「担心错过，经常自己去查」
「隔了两天才打开页面才发现」。

**规则**：审核通过/拒绝、候补递补、活动下架四类事件，向当事学生生成站内通知；
导航栏显示未读数，通知正文说明「发生了什么 + 现在做什么」。

**验收标准**：
1. 教师通过/拒绝申请后，学生在通知中心看到对应条目，未读数 +1；
2. 候补递补时，被递补学生收到通知，内容包含活动名与新状态；
3. 通知可标记已读，已读后未读数减少；
4. 通知只发给当事学生，不泄漏给其他人。

### R-15 我的报名状态透明

**来源**：候补等待中位 18.1 小时；反馈「之前以为还在候补，过了一阵再看已经是成功了」。

**规则**：「我的报名」列出每条记录的状态、**状态更新时间**、候补位次与前方人数，
并说明该状态的下一步。

**验收标准**：
1. 候补记录显示「第 N 位 / 前面还有 N-1 人」；
2. 每条记录显示 `decided_at`（状态更新时间），无则为提交时间；
3. 状态旁有一句人话解释（如「名额满后会按顺序补位」）。

### R-16 列表快捷筛选与卡片信息密度

**来源**：详情/列表 = 1.07，单会话平均打开 4.3 个详情；反馈「想找周末的」
「只想参加一类」「标题看着差不多」。

**规则**：列表页提供时间（本周末 / 未来 7 天）、「仅看还有名额」、「仅看无需审核」
三类快捷筛选；卡片直接给出**剩余名额、候补人数、报名截止剩余时间、是否需要审核、
我是否已报名**，让用户不必点进详情就能排除。

**验收标准**：
1. 三个筛选参数可单独或组合生效，并保留在 URL 中；
2. 卡片显示剩余名额与候补人数；需审核活动有明确标记；
3. 已报名的活动在列表中可直接看出状态；
4. 移动端（375px 宽）列表为单列、工具条纵向排列，不出现横向滚动。

## 3. 影响分析

| 受影响部分 | 影响 | 处理 |
|---|---|---|
| `Registration` 表 | 幂等需要记录提交令牌 | 新增 `SignupAttempt` 表，不动现有唯一约束 |
| `registration_service.signup()` | 返回值从 `(bool, str)` 变为结构化结果 | 保留兼容包装，路由改用结构化结果 |
| 报名路由 | 提交后改为重定向到结果页 | 新增 `/registrations/result` |
| 教师审核 / 取消报名 | 需要产生通知 | 在 service 的提交点写入 `Notification` |
| 活动列表 | 新增筛选参数与卡片字段 | 只加参数，不改原有 `q/category/status` 语义 |
| 既有测试 | `test_05b` 断言的「请勿重复报名」与 R-10 冲突 | 按新规则更新该条断言，其余保持 |
| 数据库 | 新增 2 张表 | `db.create_all()` 自动建表，无需迁移脚本 |

## 4. 明确不做的事

1. **不做海报文字放大、地点说明补充**：仅 6 条反馈、无行为证据，且属于内容运营而非系统能力；
2. **不做短信/邮件/微信推送**：涉及外部通道与真实凭据，实验环境无法验证，站内通知已能覆盖「可感知」这一核心问题；
3. **不做推荐算法**：数据里没有曝光/点击的负样本，做不出可信的推荐，属于过度设计。
