# V3.0 设计调整

> 对应需求：R-10 ~ R-16（见 `docs/07-V3.0需求演化.md`）
> 本文只记录**与 V2.0 不同**的设计决策，未提及的部分沿用 `docs/03-软件设计.md`。

## D-12 幂等键落库，而不是放在会话里

**问题**：重复提交要「返回第一次的结果」，就必须把第一次的结果存下来。

**方案对比**：

| 方案 | 跨刷新 | 跨设备 | 可审计 | 结论 |
|---|---|---|---|---|
| 前端禁用按钮 | 否 | 否 | 否 | 只能挡住双击，挡不住刷新与网络重发 |
| Session 存结果 | 是 | 否 | 否 | 会话丢失后无法复现结果 |
| **独立 `SignupAttempt` 表** | **是** | **是** | **是** | **采用** |

`SignupAttempt` 以 `token` 唯一索引为幂等键，记录本次提交的
`user_id / activity_id / result_code / message / created_at`。
第二次携带同一 token 的请求直接读这张表返回，不再进入业务判断。

不把 token 放进 `Registration` 表，是因为报名记录要长期保留、且一活动一学生只有一条；
提交尝试是**行为流水**，生命周期与报名记录不同，混在一起会让唯一约束变复杂。

## D-13 报名结果改为结构化对象

V2.0 的 `signup()` 返回 `(bool, str)`，视图层只能把字符串塞进 flash。
这导致「原因」和「下一步」无法分开呈现，也无法给出稳定错误码。

V3.0 返回 `SignupResult`：

```python
@dataclass(frozen=True)
class SignupResult:
    ok: bool            # 是否达成用户意图（重复提交也算达成）
    code: str           # SIGNUP_OK / SIGNUP_WAITLIST / SIGNUP_DUPLICATE_IDEMPOTENT ...
    status: str | None  # 报名状态
    message: str        # 一句话结论
    reason: str         # 为什么会这样
    next_step: str      # 现在能做什么
    retryable: bool     # 是否值得重试
    position: int | None
```

**关键语义变化**：`ok` 表示「用户的意图是否已经实现」，而不是「这次请求是否被接受」。
重复提交时意图早已实现，因此 `ok=True`、`code=SIGNUP_ALREADY_REGISTERED`，
不再返回「请勿重复报名」这种否定句式。

## D-14 结果页用 token 寻址，不用 session 暂存

提交成功后重定向到 `/registrations/result/<token>`，页面从 `SignupAttempt` 读取快照。

- 刷新结果页是纯 GET，不会产生新的报名请求；
- 链接可回看、可收藏，换设备打开也能看到（仍校验 `user_id`，非本人 404）；
- 不依赖 session，测试里可以直接断言页面内容。

结果页同时承担 R-11 的「原因 / 下一步」展示，失败与成功共用同一模板，只是配色与文案不同。

## D-15 满员竞态一律转候补

V2.0 在「提交瞬间名额已满」时其实已会转入候补，但 `capacity_conflict` 这类
上游判定仍可能把请求挡在业务层之前。V3.0 明确：**名额状态以提交时的数据库状态为准，
满了就进候补，不产生冲突错误**。

因此 `SIGNUP_FULL` 在本系统中不再是一个失败码，而是一个带位次的候补结果
（`SIGNUP_WAITLIST`）。这样 41 次「白跑」的请求会变成 41 个明确的候补位次。

## D-16 通知在业务提交点同事务写入

`Notification` 表字段：

| 字段 | 说明 |
|---|---|
| `user_id` | 接收者（只发给当事学生） |
| `kind` | `review_approved` / `review_rejected` / `waitlist_promoted` / `activity_canceled` |
| `title` / `body` | 发生了什么、现在做什么 |
| `link_url` | 直达活动或「我的报名」 |
| `activity_id` | 关联活动，便于去重与排查 |
| `created_at` / `read_at` | 生成与已读时间 |

**写入位置**：与状态变更在同一个 `db.session.commit()` 内。
如果状态改了而通知没写成功，用户就会再次陷入「状态变了但我不知道」——
这正是数据里 32 人在 72 小时内没看过状态页的原因。同事务保证两者要么都成功、要么都回滚。

未读数通过 `context_processor` 注入模板，每次渲染导航栏时按 `user_id` 计数。
数据量小（单用户几十条），不做缓存。

## D-17 列表筛选：新增维度在内存层，沿用 V2.0 的既有判断

活动状态（`Activity.status`）是由时间推导的属性，无法用 SQL 过滤，
V2.0 已在 Python 层做状态筛选（设计决策 D3）。V3.0 的三个新维度中：

- `vacancy`（仅看有名额）依赖 `approved_count`，同样只能内存过滤；
- `review`（仅看无需审核）是数据库字段，可以下推到 SQL；
- `when`（本周末 / 未来 7 天）是时间区间，可以下推到 SQL。

为了保持代码可读性，`when` 与 `review` 下推到查询，`vacancy` 在内存层过滤，
与原状态筛选放在同一段，避免两套筛选逻辑分叉。

**「本周末」的口径**：以周六 00:00 至周日 24:00 为准；若当天是周日，
则指「今天」所在周末，避免出现「本周末」指向下周的歧义。

## D-18 卡片信息密度与移动端

卡片新增四项，全部来自模型现有属性，不新增查询：

- 剩余名额 / 不限（`Activity.remaining`）
- 候补人数（`Activity.waitlist_count`）
- 截止剩余时间（由 `signup_deadline` 与 `now()` 计算，模板过滤器）
- 我是否已报名及状态（`Activity.registration_of(current_user)`）

移动端（≤640px）：工具条纵向排列、卡片单列、卡片内元信息不换行截断。
数据中移动端占 71%，这一条不是「顺手优化」，而是主要使用场景。

## D-19 对既有测试的影响

V1.0 的 `test_05b_重复报名被拒绝` 断言页面包含「请勿重复报名」。
该断言与 R-10 直接冲突——R-10 要求重复报名返回**成功语义**。

处理：保留用例编号与「不产生第二条记录」的断言，把文案断言改为
「已提交过报名，当前状态」。这是规则演进导致的用例更新，在提交信息中注明，
不做「为了让测试通过而放宽断言」的处理。

其余 V1.0 / V2.0 用例的断言不涉及本次改动的文案，全部保持原样运行。
