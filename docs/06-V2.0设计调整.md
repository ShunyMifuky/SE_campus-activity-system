# 校园活动管理系统 V2.0 · 设计调整说明

> 对应《V2.0 需求演化说明》中确认的 R-01 ~ R-09 与 US-01 ~ US-09。
> 本文件说明：需求变化对 V1.0 的影响，以及本轮对设计的调整与理由。

## 一、影响分析

本轮变化集中在**报名这条主链**上：由 V1.0 的「先到先得、一步生效」扩展为
「申请 → 审核（可选）→ 正式参加或候补 → 释放与递补」的多状态流程。

| 变更项 | V1.0 原情况 | V2.0 确认后的变化 | 受影响模块／数据／流程 | 处理方式 |
|---|---|---|---|---|
| 满员后的处理 | 满员直接拒绝报名 | 满员后仍可提交申请，进入候补队列 | `registration_service.signup()`；报名记录；活动详情页报名面板 | 修改报名逻辑：满员不再拒绝，改为创建「候补中」记录 |
| 报名状态 | 报名即生效，无状态字段 | 待审核／已通过／候补中／未通过／已取消 | 报名记录新增状态字段；所有读写报名的服务与页面 | 新增字段；V1.0 已有记录迁移为「已通过」 |
| 空位释放与递补 | 取消只是删除记录 | 取消后自动把空位给候补最靠前者 | `registration_service` 取消逻辑；报名状态 | 在取消的同一事务内完成递补 |
| 报名审核 | 无审核环节 | 活动可设为「需要审核」，教师审本人活动，先资格后名额 | 活动新增字段；新增审核动作；教师端新增待审核入口 | 新增字段与入口；审核结果与名额、候补联动 |
| 参加资格 | 报名无条件限制 | 活动可填写资格条件说明（可选） | 活动新增字段；活动详情页 | 新增字段与展示；条件由审核把关，不自动拦截 |
| 角色与平台管理 | 仅学生与教师 | 增加系统管理员 | 用户角色取值；新增管理员模块；活动可见范围 | 新增角色与模块；管理员不介入报名业务 |

**总体影响**：数据层新增 4 个字段、扩展 1 个角色取值；业务层重写报名与取消两个核心动作；
表示层新增待审核入口与管理员页面；V1.0 的活动发布、浏览、详情能力不受影响，
但报名相关的测试用例需要按新规则重写，并保留原有核心流程的回归验证。

## 二、数据模型调整

### 2.1 报名记录：新增状态字段

```python
REG_PENDING   = "pending"    # 待审核
REG_APPROVED  = "approved"   # 已通过（正式参加）
REG_WAITLIST  = "waitlist"   # 候补中
REG_REJECTED  = "rejected"   # 审核未通过
REG_CANCELED  = "canceled"   # 已取消
```

`(activity_id, user_id)` 的**唯一约束保留不变**——它仍然是防止重复报名的最终防线。
状态字段只描述"这条报名现在处于什么阶段"，不改变一活动一学生一条记录的结构。

> **设计决策 D6：状态用显式字段，而不是像活动状态那样由时间推导。**
> 活动状态（V1.0 的 D3）可以由时间算出来，因为"是否截止、是否开始"完全由时间决定；
> 但报名状态由**事件**驱动——教师审核、他人取消触发递补，这些无法从时间推导。
> 两类状态性质不同，因此处理方式也不同。

### 2.2 活动：新增审核开关与资格说明

```python
requires_review  = db.Column(db.Boolean, nullable=False, default=False)
eligibility_note = db.Column(db.String(200), nullable=False, default="")
```

- `requires_review` 默认 `False`：**保持 V1.0 行为不变**，不给存量活动凭空增加一道等待。
- `eligibility_note` 只是说明文字，由人（教师）在审核时判断，系统不做自动筛选——
  访谈中教师说的是"有明确参加条件时我才需要逐个确认"，条件本身可能是年级、专业、
  是否参加过前置活动等，无法用简单字段表达。

### 2.3 名额口径（关键调整）

V1.0 的 `registered_count` 等于全部报名记录数。V2.0 改为：

| 属性 | 含义 |
|---|---|
| `approved_count` | 状态为「已通过」的记录数 → **只有它占用名额** |
| `waitlist_count` | 状态为「候补中」的记录数 |
| `pending_count` | 状态为「待审核」的记录数 |
| `is_full` | `capacity > 0 and approved_count >= capacity` |

> **设计决策 D7：待审核与候补中的记录都不占名额。**
> 若待审核占名额，教师一拒绝就要再释放名额，顺序还会影响其他学生；
> 若候补占名额，等于满员后就再也进不来人。两者都违背访谈确认的规则。

### 2.4 用户：新增管理员角色与账号启用状态

```python
ROLE_ADMIN = "admin"
enabled = db.Column(db.Boolean, nullable=False, default=True)

@property
def is_active(self):        # 覆盖 UserMixin 的默认实现
    return self.enabled
```

> **设计决策 D8：账号停用借 `is_active` 实现。**
> Flask-Login 在登录与 `login_required` 检查时都会读 `is_active`，
> 覆盖它即可让停用账号**无法登录**，而不必在每个入口手写判断，避免遗漏。
> 账号停用**不改动其报名记录**（见需求演化说明第六节）。

## 三、报名流程调整

V1.0 是一条直线：校验 → 创建记录即生效。V2.0 变成分支流程：

```
学生提交报名
   │
   ├─ 角色校验（非学生 → 拒绝）
   ├─ 活动已下架 → 拒绝
   ├─ 报名已截止 → 拒绝
   ├─ 已有未取消的记录 → 拒绝（提示重复报名）
   │
   └─ 判定分支
        ├─ 活动「需要审核」 → 状态 = 待审核（不占名额）
        └─ 活动「不需要审核」
             ├─ 尚有名额（或人数不限） → 状态 = 已通过（正式参加）
             └─ 名额已满              → 状态 = 候补中
```

**取消报名**：V1.0 是删除记录，V2.0 改为置为「已取消」并保留记录。

> **设计决策 D9：取消不删记录。**
> 需求 R-07／US-06 要求状态中包含「已取消」，删掉记录就无法展示；
> 同时唯一约束下同一活动只能有一条记录，因此**重新报名时复用这条记录**，
> 重新走一遍上面的分支判定即可。

## 四、审核流程（先资格、后名额）

教师在「待审核」列表中处理本人活动的申请：

```
教师审核（仅本人活动、仅待审核记录）
   ├─ 拒绝 → 状态 = 未通过（不占名额、不进入候补）
   └─ 通过
        ├─ 当时仍有名额（或人数不限） → 状态 = 已通过
        └─ 当时已无名额             → 状态 = 候补中
```

> **设计决策 D10（已修订）：候补顺序按「进入候补的时间」升序，取
> `Registration.waitlisted_at`。**
> 访谈中教师明确"候补要有明确先后，按进入候补的时间处理"。
>
> 首版实现取 `Registration.created_at`（报名时间）升序，理由是"不让先提交、
> 先通过资格的人排到后面"。该口径在**不需审核**的活动里与规则等价（报名即入队），
> 但在**需审核活动 + 教师审核顺序与报名顺序不一致**时会分叉：先报名但后通过的人
> 会排到先通过的人前面 —— 这属于对已确认规则的改动，而任务说明第八条明确不允许
> 因实现方便改变已确认的规则。
>
> 现修订为：真正转入候补时记录 `waitlisted_at`，候补顺序以该时刻为准。
> 副作用是明确的——先报名但审核较慢的人，候补位次会排到后面，这是访谈规则的直接
> 含义。同一时刻入队的（`now()` 精确到秒）按报名先后排序。
> 固化用例：`TEST-V2-15b`（审核顺序与报名顺序相反时仍按进入候补的时间排序）。

## 五、递补机制

```
正式参加者取消报名
   │
   ├─ 活动人数不限（capacity = 0） → 无需递补
   ├─ 当前已无名额空缺             → 无需递补
   ├─ 候补队列为空                 → 位置保持空缺
   └─ 否则：取进入候补最早（waitlisted_at 最小）的「候补中」记录 → 置为「已通过」
```

> **设计决策 D11：递补在同一事务内同步完成，不引入定时任务。**
> R-02 确认按系统自动处理。V1.0 是同步 Web 应用，取消动作触发时立即在同一次数据库
> 事务里完成递补，既满足"即时补位"，也避免引入后台任务与"短信提醒"这类范围外能力。

**退出候补**与**取消报名**是两个语义不同的动作（教师第 22 组明确二者不是一回事），
但都用同一条记录：状态置为「已取消」。区别在于**只有放弃正式名额时才触发递补**。

## 六、管理员模块

新增 `app/admin/` 模块与 `admin_required` 装饰器，包含两组能力：

| 能力 | 允许 | 明确不允许 |
|---|---|---|
| 账号管理 | 查看平台用户账号与状态；停用异常账号；恢复为可用 | 修改用户角色以外的账号信息；代替用户处理报名 |
| 活动监管 | 查看平台全部活动；对违规或明显错误的活动执行下架 | 修改人数上限、参加资格、候补顺序与审核结果；处理具体报名 |

> **设计决策 D12：管理员的下架复用 V1.0 已有的软下架（D5）。**
> 不新增"删除活动"这种破坏性操作——下架保留历史与报名数据，与 V1.0 一致；
> 若活动下架时仍有候补队列，候补记录一并保留（状态不变），便于追溯。

## 七、对 V1.0 的兼容处理

| 项目 | 处理 |
|---|---|
| 已有报名记录 | 迁移时一律置为「已通过」——它们在 V1.0 中就是正式生效的报名 |
| 已有活动 | `requires_review` 默认 `False`，行为与 V1.0 完全一致 |
| 已有的唯一约束 | 保留，继续作为防重复报名的最终防线 |
| 已有的权限校验 | 保留角色 + 资源归属双重校验，新增的管理员入口同样强制归属/角色校验 |
| 已有测试 | 报名相关的用例按新规则重写；活动发布、浏览、权限等用例保持并回归 |
