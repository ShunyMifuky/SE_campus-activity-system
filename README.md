# 校园活动管理系统 V2.0

> 实验一 · 基于工程意图的软件迭代开发（V1.0）
> 实验二 · 基于用户访谈的需求演化（V2.0）
> 小组：林翔宇、王泰然、唐佳涵

## 一、项目定位

学校需要一个校园活动管理系统，为活动组织和学生参与提供信息化支持。
初始业务方向只有三条：支持用户注册登录、学生能够了解和参与校园活动、
活动组织教师能够发布和管理校园活动。

**V1.0**（实验一）不追求功能数量，目标是**把「教师发布活动 → 学生浏览并报名」
这条基本业务闭环真实跑通**，并保持结构清晰、可继续迭代。

**V2.0**（实验二）在 V1.0 基础上，通过访谈学生、活动组织教师、系统管理员三个角色
自行获取需求，把报名主链从「先到先得的单一动作」扩展为
**「申请 → 审核（可选）→ 正式参加或候补 → 释放与递补」**的多状态流程，
并新增系统管理员角色。本轮同样不追求功能数量——评价重点是需求是否有访谈依据、
实现是否与确认后的业务规则一致。

## 二、技术栈

| 层次 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.11+ | —— |
| Web 框架 | Flask | 轻量、无构建链，便于逐步迭代 |
| ORM | Flask-SQLAlchemy | 数据访问与约束集中定义 |
| 会话 | Flask-Login | 登录态与角色权限校验 |
| 数据库 | SQLite | 单文件，零外部服务依赖 |
| 前端 | Jinja2 模板 + 原生 CSS/JS | 服务端渲染，不引入打包工具 |

## 三、运行方式

```bash
# 1. 创建并激活虚拟环境
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

# 2. 安装依赖
pip install -r requirements.txt

# 3. 初始化数据库（建表 + 写入活动分类、演示账号与示例活动）
python -m app.seed           # 幂等写入，已存在的数据不会重复创建
# python -m app.seed --reset  # 清空并重建；演示前建议执行，保证初始数据状态一致

# 4. 启动
python run.py
```

浏览器访问 <http://127.0.0.1:5000/>

### 推荐的演示路径

示例活动中预置了两类便于演示的数据：

| 演示内容 | 用哪个活动 | 操作路径 |
|---|---|---|
| 报名审核 | 「实验室开放日（需审核）」 | 学生报名 → 状态为「待审核」→ 教师进入该活动「报名名单」，逐个通过或拒绝 → 有名额转正式参加、无名额转候补 |
| 候补与自动递补 | 「摄影基础工作坊（名额有限）」 | 已预置 2 人正式参加 + 1 人候补 → 用 `linxiangyu` 取消报名 → 候补第一位的 `zhaoyiming` 自动转为正式参加，页面会提示已补位 |
| 账号与平台监管 | 任意活动 | 用 `admin` 登录 → 账号管理（停用 / 恢复账号）、平台活动监管（查看全部活动并下架违规活动） |

## 四、验证方式

```bash
python -m unittest discover -s tests -v
```

共 **69 条**断言：

- `tests/test_business.py` —— V1.0 原有 30 条（TEST-01~TEST-06 与"服务重启后数据仍存在"），
  其中 4 条因规则演进按 V2.0 新行为更新，并在用例内注明原因
- `tests/test_v2.py` —— V2.0 新增 39 条，覆盖候补入队与排序、空位自动递补、退出候补、
  报名审核、先资格后名额、状态可见性、管理员账号与活动监管、各角色越权拒绝

每条用例使用独立的临时数据库，只通过 HTTP 接口访问系统，不直接调用内部函数——
验证的是"用户真实能走通的路径"。详细结果见 `docs/04-验证报告.md`。

├── app/
