# 需求分析 —— 校园活动管理系统 V1.0

> 依据：实验一任务书「三、实验背景与任务」给出的三条基本业务方向。
> 本文档是工程意图（`02-工程意图.md`）与后续设计、实现、验证的唯一需求来源。

---

## 1. 业务背景

学校希望建设一个校园活动管理系统，为校园活动的组织和学生参与提供信息化支持。
任务书只确定了三条业务方向：

1. 系统需要支持用户注册和登录；
2. 学生能够通过系统了解和参与校园活动；
3. 活动组织教师能够通过系统发布和管理校园活动。

这三条只说明了**系统要有哪些角色、大致要支撑什么事**，并没有说明系统要解决什么
具体问题。因此需求分析的第一步不是"列功能"，而是先弄清楚**当前校园活动的组织
方式到底卡在哪里**。

---

## 2. 当前业务中的实际问题

对现有的活动组织方式（班级群通知、公众号推送、公告栏海报、群内接龙报名）梳理后，
归纳出以下五个突出问题：

| 编号 | 现象 | 由此造成的问题 |
|---|---|---|
| **P1** | 活动通知分散在班级群、公众号、公告栏、纸质海报等多个渠道 | 学生普遍漏看通知，活动实际参与率低于预期 |
| **P2** | 报名依靠群内接龙或纸质签名表 | 报名信息格式不统一、散落在多条消息中，无法自动汇总 |
| **P3** | 组织教师手工统计报名人数 | 统计耗时且容易出错，名额经常被突破，也有统计遗漏 |
| **P4** | 活动信息"发完即沉" | 历史活动无法查询与复用，组织经验无法沉淀 |
| **P5** | 报名归属没有记录 | 无法知道谁参加过哪些活动，无法做参与度统计 |

**归纳**：这五个问题的共同根源是——**活动信息与报名数据缺少一个统一的、可查询、
可统计的承载载体**。学生反复问"还有没有名额"，教师反复答"我数一下"，本质上是
同一个数据没有被沉淀下来。

所以 V1.0 要解决的是**载体缺失**问题，而不是"缺少一个好看的页面"。

---

## 3. 用户与用户目标

### 3.1 学生（主要用户）

- 想快速知道"最近有什么活动、什么时候、在哪里、还能不能报"
- 想在线上完成报名，不必接龙、不必私聊老师确认
- 想知道自己报了哪些活动，报了之后还能取消
- 希望报名结果是**确定的**——有名额就是有名额，不留"等老师回复"的悬念

### 3.2 活动组织教师（主要用户）

- 想把活动信息一次发布到位，之后由学生自己查询，减少重复答疑
- 想知道谁报名了、报了多少人、还剩多少名额
- 活动有变动时能修改或下架，且改动能立刻生效
- 希望人数可控，不出现超出场地承载能力的报名

### 3.3 未登录访客（次要用户）

- 希望先看到有哪些活动，再决定是否注册账号

这一类用户的存在，决定了活动列表与活动详情**应当允许未登录访问**，
否则会在第一次使用时就制造门槛。

## 4. V1.0 需求清单

以下 6 条需求是经过小组分析后**最终纳入本轮范围**的需求。每一条都可被后续设计、
实现和验证直接引用。

| 需求编号 | 用户 / 角色 | 需求描述 | 优先级 | 验收依据 |
|---|---|---|---|---|
| **REQ-01** | 学生、活动组织教师 | 系统应支持用户以「学生」或「活动组织教师」身份注册账号，并支持登录与登出；账号密码必须加密保存 | 高 | 注册后可用该账号登录成功；密码错误被明确拒绝；数据库中查不到任何明文密码 |
| **REQ-02** | 学生、活动组织教师 | 系统应区分学生与教师两种角色：教师可发布和管理活动，学生只能浏览活动与报名 | 高 | 学生账号访问活动发布页面被拒绝；教师账号可正常进入；改 URL 也无法越权 |
| **REQ-03** | 活动组织教师 | 教师可发布活动，填写名称、分类、简介、地点、开始时间、结束时间、报名截止时间与人数上限；并可修改或下架自己发布的活动 | 高 | 发布后活动出现在活动列表中；修改后详情同步更新；下架后不再出现在有效活动列表且无法报名 |
| **REQ-04** | 学生、访客 | 任何人（含未登录访客）可浏览活动列表与活动详情，并按分类、活动状态和关键词筛选 | 高 | 列表按筛选条件正确返回；详情页展示完整活动信息与当前报名人数 |
| **REQ-05** | 学生 | 学生可在报名截止时间前报名活动；在名额未满且未重复报名时报名成功；报名后可取消报名 | 高 | 报名成功后「我的报名」可见、报名人数 +1；**重复报名、名额已满、报名已截止**三种情况均被拒绝并给出明确原因 |
| **REQ-06** | 活动组织教师 | 教师可查看自己发布活动的报名名单，包含报名学生姓名、学号与报名时间，以及「已报名 / 剩余名额」统计 | 中 | 名单人数与报名记录一致；剩余名额计算正确 |

### 4.1 需求覆盖的业务过程

上述 6 条需求共同支撑**两个基本业务过程**，这两个过程构成 V1.0 的最小闭环：

**业务过程 A：教师发布并管理活动**
`登录（REQ-01）→ 进入教师工作台（REQ-02）→ 填写并发布活动（REQ-03）→ 学生在列表看到（REQ-04）→ 查看报名名单（REQ-06）`

**业务过程 B：学生查看活动并报名**
`浏览活动列表（REQ-04）→ 查看详情（REQ-04）→ 注册 / 登录（REQ-01）→ 提交报名（REQ-05）→ 在「我的报名」确认结果（REQ-05）`

两个过程在「活动」这一对象上衔接：A 的产出是 B 的输入。若缺少任何一个过程，
系统都不构成一个完整的业务闭环。

## 5. 需求取舍与范围控制

需求不是越多越好。以下 4 项取舍是本轮**主动放弃**的内容，记录在这里是为了说明
小组如何控制 V1.0 的范围，而不是遗漏。

### 取舍 1：不实现活动审核流程（教师发布即生效）

- **候选内容**：引入「管理员 / 教师 / 学生」三级角色，教师发布的活动需管理员审核后才上架
- **决定**：不纳入 V1.0
- **理由**：V1.0 的核心业务闭环是「发布 → 浏览 → 报名」，审核环节不构成该闭环成立的
  必要条件。引入审核会额外带来角色管理、活动多状态流转（待审 / 驳回 / 上架）和
  审核意见等一批附属需求，而 V1.0 尚无足够依据证明这个复杂度是必要的。
  本场景中发布者就是本校教师，信任边界清晰，审核的收益很低。
  若后续确需，可在 `activities` 表增加 `audit_status` 字段平滑扩展。

### 取舍 2：不做消息通知（邮件 / 短信 / 站内信）

- **候选内容**：活动发布后推送提醒、报名成功后站内信、活动开始前提醒
- **决定**：不纳入 V1.0
- **理由**：通知属于体验增强，不是业务成立的条件——没有通知，学生依然可以主动查询
  并完成报名。更重要的是，通知依赖外部服务（SMTP 服务器或短信网关），
  与「单机可运行、不依赖外部服务」的约束直接冲突。

### 取舍 3：不做签到、考勤与活动评价

- **候选内容**：扫码签到、实际到场统计、活动评分与评论
- **决定**：不纳入 V1.0
- **理由**：这三项都属于活动的**后置环节**。V1.0 连「发布 → 报名」这一环是否真的
  成立都还没有验证，提前实现后置功能属于典型范围蔓延。它们应当建立在报名数据
  已经被验证可靠的基础之上。

### 取舍 4：不做前后端分离架构

- **候选内容**：Vue / React 前端 + REST API 后端
- **决定**：不纳入 V1.0，采用服务端渲染
- **理由**：V1.0 的验证目标是**业务规则是否正确**，而不是前端工程能力。前后端分离会
  引入构建链、跨域配置、Token 鉴权、前端状态管理等一整套与业务规则无关的复杂度，
  在 2 学时的实验规模下会明显挤占用于验证业务规则的精力。详见设计文档 4.4 决策 D1。

## 6. 需求对 AI 建议的处理说明

需求分析阶段我们向 AI 提供了任务书的业务背景，AI 一次性给出了 **12 条**候选需求，
包含上述被砍掉的「审核流程」「消息通知」「签到」「评价」，还额外建议了
「活动图片上传」和「多校区支持」。

小组成员逐条对照「当前校园活动的实际问题（P1~P5）」进行判断：

- **采纳并合并**：注册登录、角色区分、发布活动、浏览活动、报名、取消报名、
  查看报名名单 → 合并整理为 REQ-01 ~ REQ-06
- **放弃**：审核、通知、签到、评价（理由见第 5 节）
- **放弃**：「活动图片上传」——不影响业务闭环，且引入文件存储与路径管理；
  「多校区支持」——当前业务背景中不存在多校区场景，属于无依据扩展

**结论**：AI 给出的需求只能作为候选内容，最终纳入范围的 6 条需求由小组根据 V1.0
的实际目标确定。
