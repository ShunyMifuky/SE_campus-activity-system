# 需求分析 —— 校园活动管理系统 V1.0

> 依据：实验一任务书「三、实验背景与任务」给出的三条基本业务方向；
> 需求表达方式参照《现代软件工程》第 2 章：产品目标与版本目标、系统边界与版本范围、
> 用户故事与验收标准、产品待办列表与需求拆分。
> 本文档是工程意图（`02-工程意图.md`）与后续设计、实现、验证的唯一需求来源。

---

## 1. 业务背景

学校希望建设一个校园活动管理系统，为校园活动的组织和学生参与提供信息化支持。
任务书只确定了三条业务方向：

1. 系统需要支持用户注册和登录；
2. 学生能够通过系统了解和参与校园活动；
3. 活动组织教师能够通过系统发布和管理校园活动。

这三条只说明了**系统要有哪些角色、大致要支撑什么事**，并没有说明系统要解决什么具体问题。
因此需求分析的第一步不是"列功能"，而是先弄清楚**当前校园活动的组织方式到底卡在哪里**。

---

## 2. 当前业务中的实际问题

对现有的活动组织方式（班级群通知、公众号推送、公告栏海报、群内接龙报名）梳理后，
归纳出以下五个突出问题：

| 编号 | 现象 | 由此造成的问题 |
|---|---|---|
| **P1** | 活动通知分散在班级群、公众号、公告栏、纸质海报等多个渠道 | 学生普遍漏看通知，活动实际参与率低于预期 |
| **P2** | 报名依靠群内接龙或纸质签名表 | 报名信息格式不统一、散落在多条消息中，无法自动汇总 |
| **P3** | 组织教师手工统计报名人数 | 统计耗时且容易出错，名额经常被突破，也有统计遗漏 |
| **P4** | 活动信息"发完即沉" | 历史活动无法查询与复用，组织经验无法沉淀 |
| **P5** | 报名归属没有记录 | 无法知道谁参加过哪些活动，无法做参与度统计 |

**归纳**：这五个问题的共同根源是——**活动信息与报名数据缺少一个统一的、可查询、
可统计的承载载体**。学生反复问"还有没有名额"，教师反复答"我数一下"，本质上是
同一个数据没有被沉淀下来。

所以 V1.0 要解决的是**载体缺失**问题，而不是"缺少一个好看的页面"。

---

## 3. 用户与用户目标

### 3.1 学生（主要用户）

- 想快速知道"最近有什么活动、什么时候、在哪里、还能不能报"
- 想在线上完成报名，不必接龙、不必私聊老师确认
- 希望能够取消自己的报名
- 希望报名结果是**确定的**——有名额就是有名额，不留"等老师回复"的悬念

### 3.2 活动组织教师（主要用户）

- 想把活动信息一次发布到位，之后由学生自己查询，减少重复答疑
- 想知道谁报名了、报了多少人、还剩多少名额
- 活动有变动时能修改或下架，且改动能立刻生效
- 希望人数可控，不出现超出场地承载能力的报名

### 3.3 未登录访客（次要用户）

- 希望先看到有哪些活动，再决定是否注册账号

这一类用户的存在，决定了活动列表与活动详情**应当允许未登录访问**，
否则会在第一次使用时就制造门槛。

---

## 4. 系统边界与版本目标

### 4.1 系统边界（系统管到哪里）

| 边界 | 内容 |
|---|---|
| **系统内** | 记录活动信息与活动状态、保存报名记录、判断报名是否被允许、展示报名结果与名单 |
| **系统外** | 活动实际的组织与执行（申请场地、布置会场、现场签到）、线下的通知与沟通、学生的实际到场 |

边界的作用是防止软件承担它无法兑现的现实责任：V1.0 只负责"把活动信息和报名数据管起来"，
不负责"保证活动办成"。

### 4.2 版本目标（这一轮做出什么业务结果）

> **教师能够在系统里发布一个活动，学生能够看到它并在线完成报名，
> 教师能够看到完整的报名名单。**
>
> 即打通「**发布活动 → 浏览活动 → 报名活动 → 查看报名名单**」这条核心链。

这是**版本目标式表达**，而不是功能清单式表达（"做了登录页、活动表单、列表页、报名接口"）。
两者的区别在于：页面都做完不等于学生真的能完成一次报名；而版本目标可以直接用一个
完整场景来验收。

### 4.3 当前版本范围与暂不包含

| | 内容 |
|---|---|
| **当前版本范围** | 用户注册登录与角色权限、教师发布与管理活动、学生浏览活动、学生报名与取消报名、教师查看报名名单 |
| **暂不包含** | 活动审核流程、消息通知、签到考勤、活动评价、活动图片上传、多校区支持、前后端分离 |

**"暂不包含"不是永久拒绝**，而是当前迭代的边界：这些能力都有长期价值，但首个版本若
同时承诺，会挤压核心链的稳定性。它们保留在第 7 节的产品待办列表中作为后续候选。

## 5. 用户故事

用户故事把需求放回具体使用者和业务目标中，而不是只写功能名称。
每条故事按「**角色 — 能力 — 价值**」三段式书写：

> 我作为〈角色〉，我希望〈能力〉，以便〈价值〉。

需要强调的是：**用户故事不是完整需求规格**，它必须由验收标准（正常流程 / 异常流程 /
权限边界）和第 6 节的业务规则共同支撑。没有验收标准，容易把"页面做出来了"误认为需求完成。

### US-01 注册并登录系统

> **我作为**学生或活动组织教师，**我希望**能用自己的账号注册并登录系统，
> **以便**让系统确认我是谁，并以我的身份使用相应功能。

| 验收标准 | 内容 |
|---|---|
| 正常流程 | 填写账号、姓名、身份、密码后注册成功；用该账号可以登录并进入系统 |
| 异常流程 | 账号已被占用、密码少于 6 位、两次密码不一致、账号或密码错误时，系统给出明确提示且不放行 |
| 权限边界 | 未登录用户只能浏览活动列表与详情，不能报名，也不能发布活动 |
| 业务规则 | 密码必须加密保存，系统任何位置都不保留明文 |
| 对应需求 | REQ-01 |

### US-02 区分教师与学生身份

> **我作为**活动组织教师，**我希望**系统能区分教师与学生两种身份，
> **以便**活动管理这类操作不会被学生账号执行。

| 验收标准 | 内容 |
|---|---|
| 正常流程 | 教师登录后可以进入活动发布与管理入口 |
| 异常流程 | 学生账号访问活动发布入口时被拒绝并提示无权访问，手工改 URL 同样被拒绝 |
| 权限边界 | 教师只能管理**自己发布**的活动，不能编辑、下架他人活动，也不能查看他人活动的报名名单 |
| 业务规则 | 角色判断与资源归属判断必须同时进行，只判断角色不足以构成权限边界 |
| 对应需求 | REQ-02 |

### US-03 发布与管理活动

> **我作为**活动组织教师，**我希望**能发布活动并填写时间、地点、人数上限和报名截止时间，
> **以便**学生自己就能查到完整信息，不必反复来问我。

| 验收标准 | 内容 |
|---|---|
| 正常流程 | 填写完整信息后发布成功，活动出现在活动列表中；可以修改已发布活动，修改后详情同步更新 |
| 异常流程 | 名称为空、地点为空、结束时间早于开始时间、报名截止晚于开始时间、人数上限不是整数时被拒绝并提示原因；把人数上限改到低于当前已报名人数时被拒绝 |
| 权限边界 | 只有该活动的发布者本人可以修改或下架它 |
| 业务规则 | 下架采用软下架：活动记录与已有报名数据保留，只是不再出现在有效活动列表中且不可报名 |
| 对应需求 | REQ-03 |

### US-04 浏览有哪些活动

> **我作为**学生，**我希望**能在活动列表里看到有哪些活动以及每个活动的关键信息，
> **以便**判断哪个活动我想参加。

| 验收标准 | 内容 |
|---|---|
| 正常流程 | 打开列表可以看到活动名称、时间、地点、报名截止时间、当前报名人数与活动状态；点开可以看到完整简介 |
| 异常流程 | 访问不存在的活动时提示页面不存在（404），不出现空白页或错误页 |
| 权限边界 | 浏览不设角色限制，未登录访客也可以查看列表与详情 |
| 业务规则 | 活动状态（报名中 / 报名已截止 / 进行中 / 已结束 / 已下架）由当前时间与各时间字段推导得出，不作为可写字段保存 |
| 对应需求 | REQ-04 |

### US-05 在线报名活动

> **我作为**学生，**我希望**能在报名截止前在线报名活动，
> **以便**不必在群里接龙，也不必等老师确认才算报名成功。

| 验收标准 | 内容 |
|---|---|
| 正常流程 | 在报名截止前、名额未满、且未重复报名时提交，系统记录报名并提示成功；"我的报名"中可见，活动报名人数加一 |
| 异常流程 | 重复报名、名额已满、报名已截止三种情况都被拒绝，并分别说明具体原因 |
| 权限边界 | 只有学生账号可以报名；教师账号提交报名被拒绝；未登录提交报名时跳转登录页 |
| 业务规则 | 报名允许取消；取消后报名记录删除、名额释放，其他学生可以补上 |
| 对应需求 | REQ-05 |

### US-06 查看报名名单

> **我作为**活动组织教师，**我希望**能查看某个活动的报名名单和剩余名额，
> **以便**提前准备场地与材料，并知道还能不能再收人。

| 验收标准 | 内容 |
|---|---|
| 正常流程 | 名单按报名先后列出学生姓名、学号与报名时间；同时显示已报名人数、人数上限与剩余名额 |
| 异常流程 | 还没有人报名时明确提示"暂时还没有学生报名"，剩余名额正确显示；不限人数的活动显示"不限" |
| 权限边界 | 只能查看自己发布活动的报名名单，其他教师的账号访问被拒绝 |
| 业务规则 | 剩余名额 = 人数上限 − 已报名人数；有学生取消报名后名单同步更新 |
| 对应需求 | REQ-06 |

### 5.1 用户故事与需求的对应关系

| 用户故事 | 角色 | 能力 | 对应需求 | 本轮是否纳入 |
|---|---|---|---|---|
| US-01 | 学生 / 教师 | 注册并登录 | REQ-01 | 纳入 |
| US-02 | 活动组织教师 | 区分教师与学生身份 | REQ-02 | 纳入 |
| US-03 | 活动组织教师 | 发布与管理活动 | REQ-03 | 纳入 |
| US-04 | 学生 | 浏览有哪些活动 | REQ-04 | 纳入 |
| US-05 | 学生 | 在线报名活动 | REQ-05 | 纳入 |
| US-06 | 活动组织教师 | 查看报名名单 | REQ-06 | 纳入 |

六条故事共同构成第 4.2 节的版本目标：**US-03 → US-04 → US-05 → US-06 是核心链本身，
US-01 与 US-02 是核心链成立的前提（没有身份就无法判断"谁在报名""谁能发布"）**。

## 6. V1.0 需求清单与业务规则

### 6.1 需求条目

| 需求编号 | 用户 / 角色 | 需求描述 | 优先级 | 验收依据（详见第 5 节各故事） |
|---|---|---|---|---|
| **REQ-01** | 学生、活动组织教师 | 系统应支持用户以「学生」或「活动组织教师」身份注册账号，并支持登录与登出；账号密码必须加密保存 | 高 | US-01 的正常流程 / 异常流程 / 权限边界全部通过；数据库中查不到明文密码 |
| **REQ-02** | 学生、活动组织教师 | 系统应区分学生与教师两种角色：教师可发布和管理活动，学生只能浏览活动与报名 | 高 | US-02 的三类验收标准全部通过；改 URL 也无法越权 |
| **REQ-03** | 活动组织教师 | 教师可发布活动（名称、分类、简介、地点、开始与结束时间、报名截止时间、人数上限），并可修改或下架自己发布的活动 | 高 | US-03 的三类验收标准全部通过；下架后不再出现在有效活动列表且无法报名 |
| **REQ-04** | 学生、未登录访客 | 任何人（含未登录访客）可浏览活动列表与活动详情，查看活动的时间、地点、报名截止时间、当前报名人数与状态 | 高 | US-04 的三类验收标准全部通过 |
| **REQ-05** | 学生 | 学生可在报名截止时间前报名活动；在名额未满且未重复报名时报名成功；报名后可取消报名 | 高 | US-05 的三类验收标准全部通过，含三个拒绝分支 |
| **REQ-06** | 活动组织教师 | 教师可查看自己发布活动的报名名单，包含报名学生姓名、学号与报名时间，以及「已报名 / 人数上限 / 剩余名额」统计 | 中 | US-06 的三类验收标准全部通过；剩余名额计算正确 |

### 6.2 业务规则（不因压缩范围而删减）

> 范围控制的原则是**减少能力数量，但不删除核心规则**。以下规则是业务成立的前提，
> 即使 V1.0 范围再小，也不允许为了赶进度而省略。

| 编号 | 业务规则 | 对应需求 | 若省略的后果 |
|---|---|---|---|
| **BR-01** | 密码必须哈希保存，不得明文存储 | REQ-01 | 账号可直接被盗用，属于安全底线 |
| **BR-02** | 权限必须同时校验"角色"与"资源归属" | REQ-02 | 任何教师改一个 URL 就能操作他人的活动 |
| **BR-03** | 报名必须同时满足三个条件：未过报名截止、名额未满、未重复报名 | REQ-05 | 名额被突破、重复报名、截止后仍能报名，报名数据不可信 |
| **BR-04** | 活动状态由当前时间与各时间字段推导，不作为可写字段保存 | REQ-03 / REQ-04 | 出现"时间已过但状态仍显示报名中"的不一致数据 |
| **BR-05** | 只能管理自己发布的活动（资源归属） | REQ-02 / REQ-03 / REQ-06 | 教师的报名名单互相可见，活动被他人随意改动 |

### 6.3 需求覆盖的业务过程

上述 6 条需求共同支撑**两个基本业务过程**，它们构成 V1.0 的最小闭环：

**业务过程 A：教师发布并管理活动**
`登录（REQ-01）→ 进入教师工作台（REQ-02）→ 填写并发布活动（REQ-03）→ 学生在列表看到（REQ-04）→ 查看报名名单（REQ-06）`

**业务过程 B：学生查看活动并报名**
`浏览活动列表（REQ-04）→ 查看详情（REQ-04）→ 注册 / 登录（REQ-01）→ 提交报名（REQ-05）→ 在「我的报名」确认结果（REQ-05）`

两个过程在「活动」这一对象上衔接：A 的产出是 B 的输入。若缺少任何一个过程，
系统都不构成一个完整的业务闭环。

## 7. 产品待办列表与范围控制

### 7.1 产品待办列表

产品待办列表不是任务清单，而是产品工作的入口。排序依据：**价值、成本、风险、依赖、
当前版本目标**。

| 候选事项 | 价值 | 成本 | 与本轮版本目标的关系 | 本轮结论 |
|---|---|---|---|---|
| US-01 注册并登录 | 高 | 低 | 核心链前提 | **纳入** |
| US-02 区分教师与学生身份 | 高 | 低 | 核心链前提（权限规则 BR-02） | **纳入** |
| US-03 发布与管理活动 | 高 | 中 | 核心链起点 | **纳入** |
| US-04 浏览有哪些活动 | 高 | 低 | 核心链第二环 | **纳入** |
| US-05 在线报名活动 | 高 | 中 | 核心链第三环 | **纳入** |
| US-06 查看报名名单 | 高 | 低 | 核心链终点，教师的直接收益 | **纳入** |
| 活动审核流程（管理员角色） | 中 | 高 | 不构成核心链成立条件，且需新增角色与活动多状态流转 | 后续候选 |
| 消息通知（邮件 / 短信 / 站内提醒） | 中 | 高 | 属于体验增强，且依赖外部服务，与"单机可运行"冲突 | 后续候选 |
| 签到与考勤 | 中 | 中 | 属于活动后置环节，核心链尚未验证稳定 | 后续候选 |
| 活动评价与评论 | 低 | 中 | 属于活动后置环节 | 后续候选 |
| 活动图片上传 | 低 | 中 | 不影响核心链，且引入文件存储与路径管理 | 后续候选 |
| 多校区支持 | 低 | 高 | 当前业务背景中不存在该场景，属于无依据扩展 | 后续候选 |
| 历史活动归档与检索优化 | 低 | 中 | 活动记录已保留，检索优化可等数据量增长后再做 | 后续候选 |

**动态更新**：待办列表不是一次定死的。如果后续拿到真实使用反馈（例如"学生反映找不到
想参加的活动"），会据实调整优先级，而不是现在就凭想象把功能堆进首个版本。

### 7.2 需求拆分与渐进细化

V1.0 只做核心链本身。按第 4.2 节的版本目标，核心链可拆为四个"每轮都能形成可评审结果"的小块：

1. 教师能发布一个活动（US-03）
2. 学生能看到这个活动（US-04）
3. 学生能报名这个活动（US-05）
4. 教师能看到谁报名了（US-06）

这四个小块分别独立可评审，且串起来正好是一条完整业务链。**拆分不是把完整业务链拆碎**，
而是让每一轮都尽量形成可评审的业务结果。

### 7.3 需求取舍与范围控制

以下 4 项取舍是本轮**主动放弃**的内容，记录在这里是为了说明小组如何控制 V1.0 的范围。

**取舍 1：不实现活动审核流程（教师发布即生效）**
候选方案是引入「管理员 / 教师 / 学生」三级角色、教师发布的活动需管理员审核后才上架。
该环节不构成核心链成立的必要条件，却会额外带来角色管理、活动多状态流转（待审 / 驳回 /
上架）和审核意见等一批附属需求，而本场景中发布者就是本校教师，信任边界清晰，审核收益很低。
若后续确需，可在 `activities` 表增加 `audit_status` 字段平滑扩展。

**取舍 2：不做消息通知（邮件 / 短信 / 站内信）**
通知属于体验增强，不是业务成立的条件——没有通知，学生依然可以主动查询并完成报名。
更重要的是通知依赖 SMTP 服务器或短信网关等外部服务，与「单机可运行、零外部依赖」的
约束直接冲突。

**取舍 3：不做签到、考勤与活动评价**
这三项都属于活动的**后置环节**。V1.0 连"发布 → 报名"这一环是否真的成立都还没有验证，
提前实现后置功能属于典型范围蔓延。

**取舍 4：不做前后端分离架构**
V1.0 的验证目标是**业务规则是否正确**，而不是前端工程能力。前后端分离会引入构建链、
跨域配置、Token 鉴权、前端状态管理等一整套与业务规则无关的复杂度，在 2 学时的实验规模下
会明显挤占用于验证业务规则的精力。

### 7.4 本轮明确"不缩减"的内容

按范围控制原则，以下内容虽然不增加业务能力，但**不能删**：

- 全部业务规则 BR-01 ~ BR-05（权限、必填、名额、截止时间、状态边界）
- 六条用户故事各自的异常流程与权限边界验收标准
- 密码哈希、资源归属校验等安全底线

**一个页面很多、入口很多但核心流程不稳定的版本，不如范围更小但链条完整的版本。**
反过来，为了把范围做小而删掉权限校验或名额限制，得到的是"粗糙版本"，不是"最小原型"。

## 8. AI 建议与小组复核记录

### 8.1 需求候选的复核

需求分析阶段我们向 AI 提供了任务书的业务背景，AI 一次性给出了 **12 条**候选需求，
包含审核流程、消息通知、签到考勤、活动评价、活动图片上传、多校区支持等。
小组成员逐条对照第 2 节的真实问题（P1~P5）与第 4.2 节的版本目标进行判断：

- **采纳并合并**为 REQ-01 ~ REQ-06（即 US-01 ~ US-06）
- **放弃**审核、通知、签到、评价、图片上传、多校区，理由见第 7.3 节
- **放弃**"活动统计报表"——AI 建议按学院、按活动类型出统计图。判断：V1.0 的报名数据量很小，
  教师看报名名单上的数字就够了，报表属于在第 1 节所述问题之外凭空增加的展示需求

### 8.2 用户故事的复核（本次新增）

在按要求补充用户故事时，AI 又给出了若干故事，我们逐条过了一遍，重点检查三件事：
**角色是否真实存在、能力是否落在本轮范围内、价值是否说得通**。

| AI 给出的用户故事 | 小组判断 | 处理 |
|---|---|---|
| "我作为**管理员**，我希望审核教师发布的活动……" | 本轮没有管理员角色，且审核流程已在 7.3 取舍 1 中放弃 | **放弃** |
| "我作为学生，我希望**给活动点赞和评论**……" | 属于活动后置环节，不构成核心链 | **放弃** |
| "我作为教师，我希望**系统自动给学生发报名提醒**……" | 依赖外部服务，与约束 C5 冲突；且属于体验增强 | **放弃** |
| "我作为学生，我希望看到活动列表和关键信息" | 角色真实、能力在本轮范围内、价值成立 | **采纳**，整理为 US-04 |
| "我作为教师，我希望看到谁报名了" | 同上，且是教师的直接收益 | **采纳**，整理为 US-06 |
| "我作为学生，我希望报名活动" | 同 US-04 | **采纳**，整理为 US-05 |
| "我作为教师，我希望活动人数不超过场地容量" | 表述偏"想要一个校验"，改写为教师视角的真实诉求后保留 | **改写后采纳**，形成 US-03 中的"人数上限"与 BR-03 |
| "我作为已报名的学生，我希望取消报名" | 价值成立，成本很低 | **采纳**，作为 US-05 的业务规则 |

复核中另外做了两处收紧，避免故事写成"功能清单"：

1. US-04 原本被写成"我希望能按分类、关键词、状态检索活动"。判断：这是"想要一个检索入口"，
   属于**实现手段而不是使用者目标**——学生真正的目标是"知道有哪些活动、哪个我想去"。
   因此改为"能看到有哪些活动以及关键信息"，**不单独设立检索能力、不新增检索页面**；
   列表页上保留的分类、报名状态与关键词输入只是列表的浏览辅助（对应"看到有哪些活动"），
   不构成一条独立需求，也不进第 6.1 节的需求清单。后续若活动数量明显增长，
   再把"检索"作为独立候选事项放回第 7.1 节的待办列表。
2. US-01 原本把"注册"和"登录"写成两个故事。判断：对使用者来说这是同一个目标
   （"让系统知道我是谁"），合并为一个故事，避免为了凑数量而拆分。

**结论**：AI 给出的用户故事只是候选内容。最终纳入的 6 条故事由小组根据第 4.2 节的版本
目标和第 7.4 节"不缩减核心规则"的原则确定——**能力数量做减法，业务规则一条不减**。
