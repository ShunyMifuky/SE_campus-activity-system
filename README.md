# 校园活动管理系统 V3.0

> 实验一 · 基于工程意图的软件迭代开发（V1.0）
> 实验二 · 基于用户访谈的需求演化（V2.0）
> 实验三 · 基于运行数据的持续演进（V3.0）
> 小组：林翔宇、王泰然、唐佳涵

## 一、项目定位

学校需要一个校园活动管理系统，为活动组织和学生参与提供信息化支持。
初始业务方向只有三条：支持用户注册登录、学生能够了解和参与校园活动、
活动组织教师能够发布和管理校园活动。

**V1.0**（实验一）把「教师发布活动 → 学生浏览并报名」这条基本业务闭环真实跑通。

**V2.0**（实验二）通过访谈三个角色获取需求，把报名主链从「先到先得的单一动作」
扩展为**「申请 → 审核（可选）→ 正式参加或候补 → 释放与递补」**的多状态流程，
并新增系统管理员角色。

**V3.0**（实验三）的输入不再是访谈，而是**一批模拟运行数据**（24 个活动、
2748 次报名请求、1006 条候补变化、112 条反馈、792 条日志）。本轮先从数据中定位问题，
再自主决定改什么：

| 数据发现 | 对应需求 |
|---|---|
| 126 次重复提交全部来自客户端重试，且这些组合最终**全部报名成功** | R-10 提交幂等 |
| 41 次满员冲突平均耗时 1290ms，以错误码结束 | R-11 / R-12 失败可解释、满员转候补 |
| 递补 130 人，112 人中 32 人在 72 小时内从未查看状态页 | R-14 状态变化通知 |
| 详情浏览 5424 次 > 列表浏览 5058 次，单会话平均打开 4.3 个详情 | R-16 快捷筛选与卡片信息密度 |

> 数据边界：这批数据**不是本系统产生的**，只用于判断「哪里可能有问题」，
> 不作为 V3.0 改造效果的证据。V3.0 的效果一律由本仓库的测试与实测说明。

完整推导见 `docs/07-V3.0需求演化.md`，设计取舍见 `docs/08-V3.0设计调整.md`。

## 二、技术栈

| 层次 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.11+ | —— |
| Web 框架 | Flask | 轻量、无构建链，便于逐步迭代 |
| ORM | Flask-SQLAlchemy | 数据访问与约束集中定义 |
| 会话 | Flask-Login | 登录态与角色权限校验 |
| 数据库 | SQLite | 单文件，零外部服务依赖 |
| 前端 | Jinja2 模板 + 原生 CSS/JS | 服务端渲染，不引入打包工具 |

## 三、运行方式

```bash
# 1. 创建并激活虚拟环境
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

# 2. 安装依赖
pip install -r requirements.txt

# 3. 初始化数据库（建表 + 写入活动分类、演示账号与示例活动）
python -m app.seed           # 幂等写入，已存在的数据不会重复创建
# python -m app.seed --reset  # 清空并重建；演示前建议执行，保证初始数据状态一致

# 4. 启动
python run.py
```

浏览器访问 <http://127.0.0.1:5000/>

数据库文件位于 `instance/campus.db`，已被 `.gitignore` 排除，不会进入版本库。

### 推荐的演示路径

| 演示内容 | 用哪个活动 | 操作路径 |
|---|---|---|
| **重复提交不再报错**（R-10） | 任意有名额的活动 | 学生报名后返回详情再提交一次 → 落到结果页，显示「你已于 … 提交过报名，当前状态：已通过」，记录数不变 |
| **结果页可回看**（R-13） | 任意活动 | 报名后停在 `/registrations/result/<凭据>`，刷新三次仍是同一结果，不产生新记录 |
| **候补递补 + 通知**（R-14） | 「摄影基础工作坊（名额有限）」 | 已预置 2 人正式参加 + 1 人候补 → `linxiangyu` 取消报名 → `zhaoyiming` 自动转正，**其通知中心出现「候补成功」** |
| **审核结果通知**（R-14） | 「实验室开放日（需审核）」 | 学生报名 → 教师通过/拒绝 → 学生通知中心收到对应条目，导航栏未读数 +1 |
| **快捷筛选**（R-16） | 全部活动 | 列表页点「本周末」「还有名额」「无需审核」，条件可组合且保留在 URL |
| **账号与平台监管** | 任意活动 | `admin` 登录 → 账号管理、平台活动监管 |

## 四、验证方式

```bash
python -m unittest discover -s tests -v
```

共 **103 条**用例，全部通过：

| 文件 | 条数 | 覆盖 |
|---|---:|---|
| `tests/test_business.py` | 30 | V1.0 核心业务（TEST-01~06），其中 1 条按 V3.0 R-10 更新断言 |
| `tests/test_v2.py` | 39 | V2.0 候补、递补、审核、管理员、越权拒绝；1 条按 R-10 更新断言 |
| `tests/test_v3.py` | **34** | R-10 幂等 / R-11 结果结构化 / R-12 满员转候补 / R-13 结果页 / R-14 通知 / R-15 状态透明 / R-16 筛选，含 4 条回归 |

每条用例使用独立的临时数据库，只通过 HTTP 接口访问系统，不直接调用内部函数——
验证的是「用户真实能走通的路径」。

## 五、运行数据分析（可复核）

分析脚本不依赖第三方库，报告中每个数字都能复现：

```bash
python scripts/analyze_runtime_data.py \
    --data-dir <教师提供的 data 目录> \
    --out-dir  analysis

python scripts/make_exp3_charts.py \
    --metrics analysis/metrics.json \
    --data-dir <data 目录> \
    --out-dir  analysis/charts
```

输出：

- `analysis/metrics.json` —— 全部统计量（供报告引用）
- `analysis/report_tables.md` —— 人可读的表格
- `analysis/charts/*.png` —— 报告插图

口径约定写在脚本头部：**请求数 ≠ 人数、访问次数 ≠ 浏览人数、反馈先按文本去重**。
