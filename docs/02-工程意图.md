# 工程意图 —— 校园活动管理系统 V1.0

> 本文档在需求分析（`01-需求分析.md`）确认之后、正式编码之前形成。
> 它是后续软件设计、开发实现和软件验证的共同依据；
> 实现过程中若与本文档冲突，应先回到这里重新判断，再决定改什么。

---

## 1. 为什么建设当前版本（建设目的）

**直接动因**：当前校园活动的信息与报名数据分散在班级群、公众号、公告栏和纸质接龙表里，
学生漏看通知、教师手工统计，活动组织效率低且无法沉淀（详见需求分析 P1~P5）。

**本轮建设目的**：用最小代价验证一个判断——
**"校园活动的发布与报名可以收敛到一个统一的信息化载体中，并且这个载体的运行成本
低到可以被日常使用接受"**。

需要强调的是：V1.0 是**可行性验证版本**，不是**功能完整版本**。它的成功标准是
"证明这条路走得通、业务规则立得住"，而不是"功能覆盖得全"。这一点直接决定了下文
第 2 节的范围边界——凡是不能帮助验证这个判断的内容，本轮都不做。

---

## 2. 当前版本主要解决什么问题

对应需求分析中的 P1~P5，V1.0 只解决其中与「发布 → 报名」闭环直接相关的部分：

| 原问题 | V1.0 是否解决 | 解决方式 |
|---|---|---|
| P1 通知分散、容易漏看 | **部分解决** | 提供统一的活动列表，学生有一个固定地方可查；主动推送不做 |
| P2 报名靠接龙、无法汇总 | **解决** | 报名线上化，系统直接落库，格式统一 |
| P3 手工统计、易出错、易超员 | **解决** | 报名人数自动统计；人数上限在报名时由系统强制校验 |
| P4 活动信息发完即沉 | **部分解决** | 历史活动保留在库中可查询；不做活动归档与检索优化 |
| P5 报名归属无记录 | **解决** | 报名记录关联用户，可查"谁报了哪个活动" |

**本轮不解决的问题**：活动的主动触达（P1 的推送部分）、活动的后置环节
（签到 / 考勤 / 评价）。这两类明确排除在本轮范围之外。

## 3. 本轮准备完成哪些内容（本轮范围）

### 3.1 范围内（In Scope）

1. **用户与身份**：学生 / 教师两类角色的注册、登录、登出；密码哈希存储；登录态维持
2. **权限边界**：两种角色的能力区分；教师对活动的操作限定在"自己发布的"范围内
3. **活动管理（教师侧）**：发布活动、修改活动、下架活动；活动的分类归属
4. **活动浏览（公共侧）**：活动列表、分类与状态筛选、关键词检索、活动详情页；
   未登录可浏览
5. **活动报名（学生侧）**：提交报名、取消报名、"我的报名"列表
6. **报名管理（教师侧）**：查看某活动的报名名单与"已报名 / 剩余名额"统计
7. **可追溯性**：关键操作（发布 / 下架 / 报名 / 取消报名）写入操作日志表
8. **交付物**：可运行的 V1.0 代码、设计文档、验证报告、Git 版本记录

### 3.2 范围外（Out of Scope）

明确不做，且在本轮不接受"顺手加上"：

- 活动审核流程、管理员角色
- 邮件 / 短信 / 站内消息通知
- 签到、考勤、活动评价与评论
- 活动图片 / 附件上传
- 多校区、多院系组织架构
- 前后端分离、移动端 App、微信小程序
- 部署上线与域名配置（V1.0 只要求本机可运行）

## 4. 软件实现需要遵守哪些重要约束

这些约束是**硬性的**——实现方式可以变，但约束本身不能被绕过。

| 编号 | 约束 | 具体含义 |
|---|---|---|
| **C1** | 密码不得明文存储 | 注册与改密一律经哈希处理；数据库中、日志中、代码中都不允许出现明文密码 |
| **C2** | 报名必须通过三重业务校验 | 报名时同时校验：①未过报名截止时间 ②名额未满 ③未重复报名；任一不满足即拒绝并说明原因 |
| **C3** | 权限双重校验 | 既校验角色（学生不能发布活动），也校验资源归属（教师不能改别人的活动）；不得只靠前端隐藏按钮 |
| **C4** | 活动状态由数据推导，不作为可写字段 | 「报名中 / 报名已截止 / 进行中 / 已结束」由当前时间与各时间字段计算得出，避免出现状态与实际时间不一致的脏数据 |
| **C5** | 单机可运行，零外部依赖 | 数据库用 SQLite 单文件；不引入 Redis、消息队列、外部 API；不引入前端构建工具 |
| **C6** | 不提交敏感信息 | `.env`、密钥、Token、真实个人隐私数据一律不进版本库 |

## 5. 根据什么判断当前版本已经达到预期目标（完成依据）

以下 5 条是 V1.0 的**完成依据（Definition of Done）**，也是第 7 部分软件验证的对齐
目标。全部满足才认为本轮达到预期。

| 编号 | 完成依据 | 验证方式 |
|---|---|---|
| **E1** | REQ-01 ~ REQ-06 六条需求全部可从界面完整走通，无阻断性缺陷 | 按两个基本业务过程（见需求分析 4.1）各完整走一遍 |
| **E2** | 6 条验证用例 TEST-01 ~ TEST-06 全部通过 | 每一条需求至少对应一条用例；REQ-05 的三个拒绝分支必须逐一验证 |
| **E3** | 服务重启后数据仍然存在 | 关闭服务 → 重新启动 → 检查活动与报名记录是否保留 |
| **E4** | 安全性底线成立 | 数据库中查不到明文密码；学生账号即使手工改 URL 也无法访问教师功能 |
| **E5** | 需求—设计—代码—提交记录—验证用例可逐项对应 | 每条需求的编号在文档、代码注释、提交说明与测试用例中均可追溯 |

**明确不作为完成依据的内容**：页面美观度、功能数量、代码行数、性能指标。
这些都不是 V1.0 的目标（见第 1 节的建设目的）。

## 6. 工程意图对应哪些主要需求

| 工程意图要素 | 对应需求 / 用户故事 |
|---|---|
| 建设目的（活动信息与报名数据收敛到统一载体） | REQ-01、REQ-03、REQ-04、REQ-05（US-01 / US-03 / US-04 / US-05） |
| 本轮范围 1 / 2（用户身份与权限） | REQ-01、REQ-02（US-01 / US-02） |
| 本轮范围 3 / 6（教师侧能力） | REQ-03、REQ-06（US-03 / US-06） |
| 本轮范围 4 / 5（学生侧能力） | REQ-04、REQ-05（US-04 / US-05） |
| 约束 C1（密码安全） | REQ-01，业务规则 BR-01 |
| 约束 C2（报名三重校验） | REQ-05，业务规则 BR-03 |
| 约束 C3（权限双重校验） | REQ-02，业务规则 BR-02 / BR-05 |
| 约束 C4（状态推导） | REQ-03、REQ-04，业务规则 BR-04 |
| 完成依据 E1 ~ E5 | 全覆盖 REQ-01 ~ REQ-06 与 US-01 ~ US-06 |

**版本目标的单一表述**：教师能发布活动、学生能看到并报名、教师能看到报名名单
（即 US-03 → US-04 → US-05 → US-06 这条核心链，US-01 / US-02 为其前提）。

**反向确认**：REQ-01 ~ REQ-06 **每一条都能在本文档中找到归宿**，不存在"有需求但工程
意图没覆盖"的情况；同时本文档第 3 节列出的范围内事项也都能对应到具体需求，不存在
"有工程意图但没有需求支撑"的内容。两边互相闭合。

**范围与规则的分工**：工程意图的职责是"减少能力数量"（第 3.2 节范围外清单），
但按实验要求与范围控制原则，**业务规则不允许随之删减**——权限校验、必填项、
名额与截止时间校验、状态边界一律保留（见需求文档 6.2 与 7.4）。

## 7. 变更控制约定

开发过程中如出现以下情况，必须按本条约定的顺序处理，**不允许直接改代码**：

1. **发现原有需求理解有误** → 先修正 `01-需求分析.md`，再回来更新本文件，
   最后才决定改哪些代码
2. **AI 建议了新功能** → 对照第 3.2 节「范围外」清单；如属范围内遗漏，先补需求编号，
   再实现；如属范围外，一律记入报告 6.3 作为"已知未实现"，本轮不做
3. **设计调整影响本文档** → 当设计变化导致第 4 节的约束或第 5 节的完成依据发生变化时，
   先更新本文档并说明理由
4. 任何按上述流程发生的变更，都要在 Git 提交说明中体现，并记入实验报告 6.3

**本条约定本身就是实验要求的核心**：先判断需求和工程意图，再决定如何修改软件，
而不是根据 AI 的建议直接扩大或改变实现范围。
